# ~/.config/shell

Shell configuration, written once and shared by every shell.

## Layout

| File | Generated? | Contents |
| --- | --- | --- |
| `env.sh` | yes | `PATH` and exported variables |
| `aliases.sh` | yes | interactive aliases |
| `tools.sh` | yes | `mise`, `direnv`, `fzf`, `zoxide`, `atuin`, `starship` hooks |
| `functions.sh` | no | shared functions |
| `interactive.sh` | no | shared interactive setup that is logic, not data |
| `bash.sh` | no | bash-only settings |
| `zsh.sh` | no | zsh-only settings |

The generated files come from `.chezmoidata/shell.yaml` in the chezmoi source
repo. **Editing them in `~/.config/shell` accomplishes nothing** - the next
`chezmoi apply` overwrites your change. Edit the YAML, then apply.

`~/.bashrc` and `~/.zshrc` are deliberately near-identical: each guards against
non-interactive use, then sources the fragments in a fixed order.

    env  ->  <shell>  ->  aliases  ->  functions  ->  interactive  ->  tools

`env.sh` is first because everything after it needs `PATH`. The shell-specific
fragment is early so it can set a fallback prompt that `tools.sh` overrides
with starship when starship is installed. `tools.sh` is last because tool hooks
expect a finished shell to attach to.

`env.sh` is also sourced on its own by `~/.profile` and `~/.zshenv`, so login
and non-interactive shells get the same environment without paying for the
interactive machinery. Everything in it is idempotent, so the double-source
that interactive login shells cause is harmless.

## Machine-local settings

`env.sh` loads `~/.config/shell/env.local.sh` when present. Use it for environment
needed by login, interactive, and non-interactive shells; keep it idempotent.
The rc loaders read `~/.bashrc.local` or `~/.zshrc.local` last for shell-specific
customizations. These files are ignored by chezmoi.

Set `DOTFILES_SKIP_LOCAL_INTEGRATIONS=1` in the local environment to skip
third-party tool hooks and zsh completion/prompt initialization, for example
over SSH. Shared shell settings and vi bindings still apply.

To retain an existing zsh history filename, set `HISTFILE` in `.zshrc.local`.
History contents are never managed or imported by chezmoi.

## Adding a shell

### If it is POSIX-compatible (ksh, dash, ash, busybox sh)

Nothing to generate. Write the rc file, copying `dot_bashrc` and changing the
one word naming the shell-specific fragment, then add a `<shell>.sh` next to
`bash.sh` if that shell needs anything of its own. `tools.sh` already detects
the running shell at runtime and skips hooks that shell does not support.

### If it is not (fish, nushell, elvish)

Add one template that reads the same `.chezmoidata/shell.yaml` and renders it
into that shell's dialect. Nothing else moves, and the data stays in one place.
For fish, `private_dot_config/private_fish/config.fish.tmpl` would be:

```
# GENERATED by chezmoi from .chezmoidata/shell.yaml

{{ range reverse .shell.path }}
fish_add_path --path --prepend {{ . }}
{{ end }}

{{ range $name, $value := .shell.env }}
set -gx {{ $name }} "{{ $value }}"
{{ end }}

status is-interactive; or exit 0

{{ range $name, $command := .shell.aliases }}
alias {{ $name }} '{{ $command }}'
{{ end }}

{{ range .shell.init }}
if command -q {{ .cmd }}
    {{ .cmd }} {{ printf .args "fish" }} | source
end
{{ end }}
```

The only real work is the dialect: `set -gx` for `export`, piping to `source`
instead of `eval`. Aliases, environment and tool list are read, not retyped.

## Adding an alias, variable, PATH entry or tool

Edit `.chezmoidata/shell.yaml` and run `chezmoi apply`. Every shell picks it up
at once. A tool only needs its name and the subcommand that prints its startup
code, with `%s` standing in for the shell name; it is skipped silently on
machines where it is not installed.
